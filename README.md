# Журнал отдела ЗРА ООО «ЮГ»

Исходный код: [b4lk4r/ugWeeklyLog.github.io](https://github.com/b4lk4r/ugWeeklyLog.github.io). В Git хранятся код, миграции и инструкции. База, исходный Excel, локальные доступы и резервные копии остаются на обслуживающем компьютере.

Для получения кода на другом компьютере с настроенным доступом SSH к GitHub:

```powershell
git clone git@github.com:b4lk4r/ugWeeklyLog.github.io.git
cd ugWeeklyLog.github.io
```

Затем выполните раздел первичной установки ниже. Для переноса заполненной базы используйте отдельную резервную копию и процедуру восстановления; клонирование репозитория не переносит данные. Храните секреты и копии отдельно от Git.

Локальная тестовая версия с React/TypeScript, Express и PostgreSQL. Это работающий сервер с постоянной базой, а не статический макет. **Перед подключением сотрудников требуется закончить браузерную приёмку и согласовать применение импорта.** Предоставленная тестовая книга исследована; [выводы и сопоставление полей](docs/EXCEL_ANALYSIS.md). Данные предоставленной тестовой книги загружены по указанию пользователя; внешней публикации нет. Актуальный состав и правила просмотра: [заполненная локальная версия](docs/LOCAL_PREVIEW_DATA.md).

## Быстрый просмотр на этом компьютере

Откройте http://127.0.0.1:4180. Для локального просмотра созданы три тестовых пользователя; случайные пароли находятся только в `.local/preview-credentials.json`. Не пересылайте этот файл и не используйте тестовые аккаунты для сотрудников. Пользовательские данные и пароли не включены в исходный код.

Все команды ниже выполняются в PowerShell из каталога проекта. В Windows используйте `npm.cmd`, чтобы не менять политику выполнения скриптов npm.

```powershell
cd 'C:\Users\alimb\OneDrive\Рабочий стол\week log\zra-app'
# Запуск существующей установки:
powershell -ExecutionPolicy Bypass -File scripts/start.ps1
```

Если порт 4180 уже занят этим приложением, оно уже запущено. Не запускайте второй экземпляр. Для остановки нажмите Ctrl+C в терминале запуска или выполните:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/stop-app.ps1
# Отдельно остановить ТОЛЬКО кластер проекта:
powershell -ExecutionPolicy Bypass -File scripts/stop-db.ps1
```

Существующая служба PostgreSQL на 5433 не изменялась. Наш отдельный кластер работает на 55432 и слушает только 127.0.0.1. Данные сохраняются в `.local/pgdata`; остановка приложения их не удаляет.

## Первичная установка на чистом компьютере Windows

Требуются Node.js, npm и PostgreSQL с утилитами `initdb`, `pg_ctl`, `pg_dump`, `pg_restore`. На обследованном компьютере: Windows 11 Home, Node 26.13, npm 11.20, PostgreSQL 18.3; Docker не обнаружен. Свободно около 24 ГиБ. Службы IIS/nginx/Apache не обнаружены; существующие порты и сервисы не перенастраивались.

```powershell
npm.cmd ci
# При другом расположении PostgreSQL измените $pgBin в setup-local.ps1.
powershell -ExecutionPolicy Bypass -File scripts/setup-local.ps1
npm.cmd run admin
npm.cmd run build
powershell -ExecutionPolicy Bypass -File scripts/start.ps1
```

`setup-local.ps1` не перезаписывает существующий `.env`, создаёт отдельный кластер и базы `zra`, `zra_test`, `zra_restore`. Пароли базы генерируются случайно. Приложение работает под ролью БД `zra`, не имеющей прав суперпользователя. Пароль владельца локального кластера сохранён отдельно в `.local/owner-password`; приложению он не передаётся. Доступ к каталогу и резервным копиям должен быть только у обслуживающего пользователя Windows.

`npm.cmd run admin` спрашивает логин, имя и пароль в интерактивном терминале, скрывая пароль. Минимум 12 символов. Секрет не передаётся в аргументах командной строки. Команда создаёт новую учётную запись и не перезаписывает существующую. Перед реальной эксплуатацией создайте своего администратора, затем отключите тестовые аккаунты.

## Пользователи

Администратор: «Администрирование → Добавить пользователя». Укажите имя, латинский логин, пароль и роль «Менеджер» или «Руководитель». Отключение и сброс пароля доступны через «Изменить». При изменении учётной записи её сессии отзываются. Самостоятельная смена пароля — «Мой профиль».

Менеджер видит и изменяет только принадлежащие ему сейчас заявки, включая через прямой API. Руководитель видит весь отдел и историю, по умолчанию только читает. Флаг редактирования руководителя задаётся индивидуально администратором. Возвращать конечный статус в работу и менять один конечный статус на другой может только администратор с причиной. Изменение даты получения требует причины у любого редактора. Физическое удаление заявок в интерфейсе не предусмотрено: ошибочные данные исправляются с сохранением истории.

## Работа и отчёт

«Журнал заявок»: поиск по номеру ЮГ, тендеру и заказчику, фильтры менеджера, статуса и дат получения. Три отдельных номера — номер заявки (C), номер тендера (D), номер заявки ЮГ (E) — сохраняются строками, ведущие нули сохраняются. Обязательны дата получения, заказчик, ответственный и статус. Номера, сумма, дата КП/СП и комментарий могут отсутствовать. Неизвестная сумма — `null`, а не ноль. Деньги хранятся точным `numeric(15,2)`, передаются строками и суммируются целыми копейками через BigInt.

Недельная страница показывает открытые старые заявки на начало периода и новые заявки по дате получения, известные на конец периода. Новая копия заявки на следующую неделю не создаётся. Закрытая в текущую неделю старая заявка остаётся в списке начального остатка этой недели и исчезает из начального остатка следующей. Будущая неделя показывает известное на данный момент состояние, это не прогноз будущих изменений.

Стандартная неделя отображается понедельник–пятница; фактический период включает выходные и заканчивается перед следующим понедельником 00:00 Москвы. В `.env` настройка `WEEKEND_POLICY=previous` — текущий режим. `next` относит субботу и воскресенье к следующему понедельнику: фактический период тогда от предыдущей субботы до следующей субботы, он показан в интерфейсе. Изменение режима меняет группировку прошлых недель: делайте его только как согласованное изменение методики, с резервной копией и записью решения. Для всех дат и событий используется Europe/Moscow (UTC+3).

Отчёт руководителя содержит общий итог, раскрываемые блоки менеджеров и расшифровку каждого показателя по нажатию. Начальный остаток использует последнюю версию строго до начала периода; конечный — последнюю версию строго до конца. Новые заявки делятся по конечному статусу на четыре непересекающиеся группы; их сумма равна «Поступило».

События побед/проигрышей учитываются за выбранный период, по одной заявке на каждый вид результата (последнее соответствующее событие недели). Поэтому при административном переоткрытии одна заявка может дать и победу, и проигрыш за неделю; история объясняет оба события. Обычные правки суммы без смены статуса повторную победу не создают. Победа из первоначального сбора также учитывается. Старый переход «Сбор → КП → Победа» не входит в «перешли и остались в КП/СП», но входит в победы. КП → СП считается только по факту перехода, одна заявка один раз за неделю, а не по конечному статусу.

Начальные и конечные остатки берут сумму соответствующей версии; события — сумму в момент события. Пустые суммы показываются отдельным числом, известные суммы суммируются без предположений. Расшифровка и показатель строятся из одного набора записей. Менеджер в разрезе отчёта определяется на соответствующий момент (начало, конец или событие). После передачи заявки другому менеджеру прошлые версии доступны руководителю и администратору; прежний менеджер больше не получает её через свои API.

Исправления записываются фактическим текущим временем. Система не предоставляет произвольную дату события задним числом. Поэтому отчёт уже завершившейся недели не меняется от последующей правки даты/статуса; факт исправления виден в истории. Это сознательное правило прозрачности первой версии. Уточнение старого отчёта требует отдельной методики корректировок, а не изменения времени в базе вручную.

«Выгрузить Excel» выгружает отчёт и лист расшифровок. В журнале отдельная кнопка выгружает все доступные пользователю заявки (без применения текущих фильтров). Суммы экспортируются десятичным текстом для сохранения точности; это зафиксированный отчёт, а не новая книга учёта с переносом формулами.

## Импорт Excel

В папке `week log` предоставлена `Отчет_ЗРА_ТЕСТОВЫЙ.xlsx`. Исследованы её 19 листов, формулы, недельные блоки и имена 8 менеджеров. Адаптер доработан для её структуры. Это тестовая книга; рабочий оригинал и транскрипция не предоставлены. Выявлены расхождения формул с требованиями и отсутствующие результаты вычисления; подробности в [анализе](docs/EXCEL_ANALYSIS.md). Теперь выполнен отдельный импорт всех недельных состояний по явному указанию пользователя; подробности в docs/LOCAL_PREVIEW_DATA.md.

1. Создайте менеджеров. Имена в книге и системе должны совпадать однозначно.
2. Администратор выбирает `.xlsx` в разделе импорта. Анализ сохраняется в базе; заявки ещё не создаются. Исходный файл не изменяется и не сохраняется на сервере.
3. Проверьте листы, найденные заголовки, строки, статусы, количество формул, предупреждения и ошибки. Заголовки и блоки менеджеров распознаются по всему листу; сопоставление в `server/import-scan.ts`. После обзора выберите один недельный лист и повторите анализ. Формулы читаются по сохранённым Excel значениям, не пересчитываются; отсутствие обязательного результата блокирует строку. Анализ не доказывает корректность формул. Листы без распознанных заголовков пропускаются с явной ошибкой.
4. «Сбор док-тов» преобразуется в «Сбор документов», «УПД выдано» — в «Победа»; преобразование видно в предупреждениях. Неизвестные статусы блокируют строку. Пустые необязательные поля сохраняются и помечаются для проверки. Неизвестная обязательная дата или менеджер блокируют строку.
5. Повторяющиеся номера, в том числе между недельными листами, и номера, уже имеющиеся в базе, блокируются как конфликтные. В первой версии UI не разрешает автоматически объединять их или выбирать победившую версию: требуется разбор исходной книги и подготовка отдельного согласованного файла открытых остатков. Не исправляйте единственный оригинал и не используйте «черновик» как источник без согласования.
6. Скачайте JSON анализа; отметьте только открытые строки без ошибок. Перед применением выполните резервное копирование. Затем подтвердите импорт.

Применение атомарно; файл узнаётся по SHA-256. Повторное применение этого файла не создаёт копий, даже после тестового отката. После анализа перед применением повторно проверяется отсутствие номера в БД и активность менеджера. Источник каждой записи — SHA-256, лист и строка — хранится в версии. Состояние известно только **на дату применения**, старая история не выдумывается. Старые даты получения сохраняются, но импорт не создаёт прошлые победы или остатки до первой известной версии. Выбор произвольной исторической даты наблюдения и массовая загрузка исторических недель не реализованы.

Отмена тестового импорта (ID виден в сохранённом анализе):

```powershell
npm.cmd run import:rollback -- UUID_ИМПОРТА
```

Откат допустим только если заявки после импорта не редактировались. Перед удалением сохраняется локальный JSON-архив данных и истории; факт отката остаётся в системном журнале. Если были изменения — восстановите резервную копию в отдельную базу и согласуйте ручную сверку. Команда не уничтожает изменения сотрудников.

## Резервное копирование и восстановление

```powershell
npm.cmd run backup
# Команда выше выводит путь. Восстановление допускается ТОЛЬКО в отдельную пустую базу:
npm.cmd run backup:verify -- 'C:\полный\путь\к\копии.dump'
```

`RESTORE_DATABASE_URL` в `.env` должен указывать на пустую базу, отличную от основной. Установка создала `zra_restore`; после первой проверки она уже не пуста. Для следующей проверки создайте ещё одну пустую базу и обновите только RESTORE_DATABASE_URL. Команда откажется затирать существующие таблицы. Восстановление выполняется одной транзакцией, проверяется наличие истории для каждой заявки; успешная проверка отмечается в `backup_runs` основной базы. Пароль PostgreSQL передаётся через окружение дочернего процесса, а не в аргументах команды.

`npm.cmd run restore -- путь.dump` выполняет такое же безопасное восстановление в RESTORE_DATABASE_URL. После сверки переключите DATABASE_URL на восстановленную базу и перезапустите приложение. Роли PostgreSQL копией базы не создаются: целевой пользователь и база должны существовать заранее.

Проверено реальное восстановление тестовой базы с 5 пользователями, 2 заявками и 4 версиями; результат сохранён локально в `.local/restore-result.json`. В `zra_restore` сейчас именно восстановленные синтетические данные тестов. Основная `zra` теперь содержит заполненную тестовую версию: 62 карточки, 835 недельных состояний и исходные ячейки сводного отчёта.

Копии содержат данные и хеши паролей: храните их вне публичного каталога с ограниченным доступом. Автоматическое расписание, шифрование копий и вынос на отдельный носитель ещё не настроены. Настройте ежедневный вызов backup в Планировщике заданий под выделенной учётной записью и регулярно проверяйте восстановление. Не считайте синхронизацию OneDrive резервным копированием активного PostgreSQL. Для эксплуатации перенесите кластер из OneDrive в отдельный локальный каталог/сервер по процедуре dump/restore.

## Обновление и защищённое размещение

Перед обновлением: backup, проверка копии, остановка своего приложения, обновление исходников, `npm.cmd ci`, `npm.cmd run build`, `npm.cmd run migrate`, запуск. Миграции нумеруются и применяются однократно в транзакции с блокировкой. Не удаляйте `.env`, `.local/pgdata` и резервные копии. Приложение не очищает базу при старте.

Публикация не выполнялась. Для сервера нужны выделенная база PostgreSQL, TLS на обратном прокси, закрытый доступ к порту БД и процесс приложения под ограниченной учётной записью. Укажите реальный HTTPS PUBLIC_ORIGIN и COOKIE_SECURE=true. Параметры HOST/PORT выбирайте с учётом инфраструктуры. При необходимости доверия прокси настройте точное число/адреса доверенных узлов в Express и проверьте ограничитель входа; не ставьте безусловное trust proxy. Сейчас ограничение входа 15 попыток / 15 минут на IP, в памяти процесса; за общим NAT это общий лимит. Для нескольких экземпляров нужен общий лимитер.

Использованы рекомендации [Express по защите приложения](https://expressjs.com/advanced/best-practice-security/) и штатный формат резервных копий [PostgreSQL pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html) / [pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html).

Не проверены визуальная компоновка, формы, вход и действия всех трёх ролей непосредственно в браузере, мобильная вёрстка и скачивание файла пользователем. HTTP-проверка главной страницы даёт 200, API-проверки ролей пройдены. До внедрения пройдите эти действия вручную либо предоставьте доступ к браузерному тестированию.

Нет интеграции 1С/Bitrix24, блокировки недель, универсальной исторической загрузки (предоставленная тестовая книга загружена отдельной локальной командой), интерфейса разрешения импортных конфликтов, административного удаления заявок, автоматического расписания резервирования, промышленного мониторинга, нагрузочного тестирования и полнотекстового индексирования/пагинации больших реестров. Текущие списки/отчёты считывают доступные данные целиком: объёмы реальной книги пока неизвестны. Для крупного архива потребуются серверные агрегаты и пагинация. По предоставленной тестовой книге неоднозначности описаны в docs/EXCEL_ANALYSIS.md; применение рабочих данных требует согласования.
